# #178 [Bug] Mouser prevents system sleep and screen timeout

> *This was generated by AI during triage.*

**State:** ready-for-agent

## Root cause (Mouser evidence)

- Reporter diagnostics (comments by flyingudonmonster and XJ-XH-L, not independently verified): `powercfg /requests` shows no request, so it is not `SetThreadExecutionState`. `GetLastInputInfo` resets about every 15 s with hands off all devices, matching the old SmartShift poll interval. Killing Mouser stops the resets. The screen only fails to turn off while the mouse is powered on. This points to periodic HID++ traffic counted as user input.
- In the reference source the poll is `_battery_poll_loop` (`core/engine.py:1367`). Intervals are now `BACKGROUND_BATTERY_POLL_INTERVAL_S = 1800` and `BACKGROUND_SMART_SHIFT_POLL_INTERVAL_S = 300` (`core/engine.py:36-37`). `_background_hid_poll_allowed` (`core/engine.py:1340`) gates polls on the frontend being visible and on system idle time (`_system_idle_seconds`, `core/engine.py:42`) being under `BACKGROUND_HID_POLL_IDLE_GRACE_S = 60` (`core/engine.py:38`). So the checked-out source already mitigates the 3.6.0 behavior (15 s, ungated); it is not the original code.
- Remaining gap: the SmartShift read in the loop is gated only on `hg.smart_shift_supported`, not on the `smart_shift_enabled` setting (`core/engine.py`, inside `_battery_poll_loop`).

Confidence: likely that periodic HID++ reads reset the Windows idle timer on some devices. The exact mechanism in the Windows HID stack is not confirmed.

## Agent Brief

**Category:** bug
**Summary:** The resident agent must never keep Windows from idling the display or system; it must not generate HID traffic that counts as user input while the user is away.

**Current behavior:**
In Mouser 3.6.0 a background thread polls the mouse over HID++ (battery, SmartShift mode) on a fixed timer. On affected setups each poll resets the Windows idle timer, so display timeout and sleep never trigger while the mouse is on.

**Desired behavior:**
The agent performs no periodic HID++ requests that are not strictly needed. Battery and scroll-mode state come from unsolicited HID++ notifications, from a read at connect, and from a read when the GUI process asks (GUI open and user active). Any remaining background read is skipped when the system has been idle for 60 s or more (`GetLastInputInfo`). The agent never calls `SetThreadExecutionState` and never creates a power request.

**Key interfaces:**
- Poll scheduler: pure function `poll_allowed(idle_secs, gui_connected, secs_since_last_poll) -> bool`, unit-testable.
- IPC request (for example `read_status`) from the GUI that triggers an on-demand battery/SmartShift read.
- Config: SmartShift polling (if kept) is skipped entirely when the feature is disabled in `config.json`.

**Acceptance criteria:**
- [ ] Unit tests for `poll_allowed`: false when idle >= 60 s, false when no GUI is connected, true otherwise (with a minimum spacing).
- [ ] With the GUI closed and the user idle, the agent sends zero HID++ requests (verified by a counter or log line).
- [ ] Source search shows no use of `SetThreadExecutionState` or `PowerCreateRequest`.
- [ ] Manual (MX Master 2S over Unifying): set display timeout to 1 minute, leave the agent running with the GUI closed, take hands off all devices; the display turns off on schedule and the `GetLastInputInfo` idle value grows without resetting.
- [ ] Battery level still appears when the GUI opens (read on demand) and updates on device notifications.

**Out of scope:**
- macOS behavior reported in the thread.
- Changing HID++ feature discovery at connect.
