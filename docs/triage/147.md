# #147 [Bug] Cannot assign Win+Shift+S shortcut - Windows intercepts key before capture

> *This was generated by AI during triage.*

**State:** ready-for-agent

## Root cause (Mouser evidence)

- In 3.6.0 the shortcut recorder used plain Qt key events. Windows gives the shell the `LWIN`/`RWIN` key-up, so Win+Shift+S opened Snipping Tool and stole focus before the combo was recorded.
- The reference already contains the fix the reporter suggested: `core/key_capture.py` (module docstring, lines 1-14) installs a `WH_KEYBOARD_LL` hook while the recorder is armed that swallows the Windows key and tracks its state itself. `classify_key_event` (`core/key_capture.py:47`) always passes injected events (`LLKHF_INJECTED`) and swallows only `VK_LWIN`/`VK_RWIN`; the hook `start(on_super_changed=...)` is at `core/key_capture.py:68` and `:103`.
- Typing mode exists too: `ui/qml/KeyCaptureDialog.qml:12` documents a plain text field ("typing") for shifted characters. `Super`/`Win` aliases are in `core/key_registry.py:14-23`; `shift+super+s` is flagged as "risky" at `core/key_registry.py:56`, which only warns.
- Comment evidence: users in the thread confirm typing text works; one reports the capture box catches `Super` but not the Up arrow (`Super+Up`). Cause of that is not located (the recorder swallows Win but the arrow press is still delivered to the dialog; behavior in the reference was not tested).

Confidence: confirmed for the Win key interception; guess for the `Super+Up` arrow case.

## Agent Brief

**Category:** bug
**Summary:** The shortcut recorder in the GUI must be able to record any combination that includes the Windows key, without the shell reacting.

**Current behavior:**
While the recorder is open, pressing Win+Shift+S launches the Snipping Tool and focus is lost; Win+Up is only partially recorded. Users must hand-edit `config.json`.

**Desired behavior:**
While the recorder is armed (and only then), the GUI process installs a low-level keyboard hook that records and swallows Win-key combinations (down and up of Win, and the keys pressed with it), so the shell does not act on them. Hook removal is guaranteed on dialog close, process exit, and error. Injected events pass through. The recorded text is canonical (`shift+super+s`). Typed text entry remains available as a fallback. The hook lives in the GUI process only, never in the resident agent, and exists only while the dialog is open.

**Key interfaces:**
- `classify_key_event(vk, flags, message) -> (swallow, super_down)`-style pure function, unit-testable.
- Shortcut canonicalizer: `canonicalize(&str) -> Result<String, ShortcutError>` using the same aliases (`win`, `windows`, `cmd`, `meta`, `super`).

**Acceptance criteria:**
- [ ] Unit tests: Win down/up swallowed; injected events never swallowed; non-Win keys not swallowed.
- [ ] Unit tests: `canonicalize("Win+Shift+S") == "shift+super+s"`; `Super+Up` canonicalizes without error.
- [ ] Manual: with the recorder open, pressing Win+Shift+S records `shift+super+s` and Snipping Tool does not open; Win+Up records `super+up` and the window is not snapped.
- [ ] Manual: after closing the dialog (OK, Cancel, or Alt+F4), Win+S works normally again (hook removed). Verify the process has no residual hook after repeated open/close cycles.
- [ ] The recorded shortcut, when triggered by a mouse button, sends Win+Shift+S with correct key-up ordering.

**Out of scope:**
- Ctrl+Alt+Del (see #149).
- Reserved-shortcut warnings text.
