# #327 [Bug] Gesture button controlling volume can only adjust one step

> *This was generated by AI during triage.* (original title is Chinese; translated)

**State:** ready-for-agent (reclassified as enhancement: Mouser works as designed; the user wants a continuous/"scrub" mode)

## Root cause (Mouser evidence)

Confidence: **confirmed** (design); user intent is clear from the steps (hold gesture button, move up/down, expect volume to keep changing with distance).

- The recognizer is deliberately one-swipe-per-flick: after the first swipe the hold locks axis+direction and re-fires only after a return stroke of at least `_min_return` and a fresh flick of `commit_distance` (`core/gesture_recognizer.py:33-36` docstring, `_step_locked` at `core/gesture_recognizer.py:282-329`, `_latch_return_seen` gate at `core/gesture_recognizer.py:306-307`). A single continuous slide in one direction therefore fires once and the volume changes by one OS step (the reporter saw "+2").
- Recognizer parameters come from `configure(...)` (`core/gesture_recognizer.py:101-110`) fed by `core/mouse_hook_base.py:151-161`.
- No distance-proportional or repeat mode exists; I did not locate any "repeat while held" option in `core/engine.py` or `core/config.py`. The reporter's device JSON and log were empty.

## Agent Brief

**Category:** enhancement
**Summary:** Add an opt-in "continuous" gesture mode: while the gesture button is held and the pointer keeps moving along a locked axis, the bound action repeats once per N pixels of travel (for volume up/down, scroll, brightness).

**Current behavior:**
Each swipe direction fires its action once per flick; continuing the slide does not repeat. Repeating requires moving back and flicking again.

**Desired behavior:**
Settings gain a `gesture_repeat` option (default off). When on, after the first swipe commits and locks axis/direction, further movement in the same direction emits an additional swipe event for every `gesture_repeat_step` pixels (default equal to the commit distance) with no return stroke required. Reversing direction beyond hysteresis unlocks (a swipe in the opposite direction then repeats symmetrically). Pausing for `settle_ms` re-arms as today. With the option off, behavior is identical to today. Event rate is capped (e.g. 20/s) and uses no unbounded queue.

**Key interfaces:**
- Gesture recognizer: new config fields `repeat: bool`, `repeat_step: f32`; stays pure (no HID/Win32 dependencies) and driven by `(dx, dy, now)`.
- `config.json` settings: `gesture_repeat`, `gesture_repeat_step` (additive; absent means off/default).
- Swipe event callback signature unchanged.

**Acceptance criteria:**
- [ ] Unit test: with repeat off, a 300 px straight slide produces exactly 1 swipe (current behavior preserved).
- [ ] Unit test: with repeat on and step 40, a 300 px straight slide produces 7 or 8 swipes in the same direction (document the rounding rule), spaced by at least the rate cap.
- [ ] Unit test: reversing past the hysteresis then continuing yields swipes in the new direction only; a pause >= settle_ms clears the lock.
- [ ] Manual (MX Master 2S, gesture up/down mapped to volume up/down): hold and slide up steadily, volume rises continuously with distance; release stops.

**Out of scope:**
- Speed-sensitive (acceleration) repeat.
- Changing default gesture behavior.
- Per-action step sizes.
