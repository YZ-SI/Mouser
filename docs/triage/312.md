# #312 [Bug] Master MX 3S not recognized after reconnecting

> *This was generated by AI during triage.*

**State:** ready-for-agent (behavior contract is clear; the exact hidapi behavior of a stale Windows BLE handle must be verified on hardware, noted in the brief)

## Root cause (Mouser evidence)

Confidence: **likely** (control flow confirmed; actual Windows BLE handle behavior after Easy-Switch not verified).

- The reporter uses Bluetooth (Easy-Switch away and back). The BLE HID path can change on re-enumeration, and the old handle may neither error nor deliver data.
- `HidGestureListener._main_loop` only recovers when a read/write throws, or after 3 consecutive request timeouts, then enters an "asleep" state that waits for a report on the *old* handle (`core/hid_gesture.py:3362-3410`). A report never arrives on a stale handle, so it waits the full `_SLEEP_TIMEOUT_S = 300` (`core/hid_gesture.py:3363,3391-3395`) before a full reconnect. Meanwhile `connected_device` is None and the UI shows no mouse. This matches "no mouse detected".
- With no UI open there are no requests, so the 3-timeout detection never starts (`core/engine.py:1340-1341`).
- Windows device arrival does not feed the HID layer: `WM_DEVICECHANGE` only reinstalls the mouse hook (`core/mouse_hook_windows.py:536-538`, `701-709`). macOS has an explicit wake -> `force_reconnect()` path (`core/mouse_hook_macos.py:465-518`; `core/hid_gesture.py:2093-2100`) that Windows lacks.
- After a failed connect the retry backoff grows to 30 s (`core/hid_gesture.py:3327-3350`), adding delay after the device is back.

## Agent Brief

**Category:** bug
**Summary:** The agent must detect a Bluetooth/receiver mouse leaving and returning (Easy-Switch, power-off, out of range) and re-establish HID++ diverts within seconds, without UI polling.

**Current behavior:**
After Easy-Switch away and back, the mouse works as a plain pointer but button remapping is dead and the GUI shows no device, possibly for minutes.

**Desired behavior:**
On `WM_DEVICECHANGE` (`DBT_DEVNODES_CHANGED`, or `RegisterDeviceNotification` for the HID class) the agent re-enumerates Logitech HID interfaces (debounced). If the enumerated path set differs from the open handle's path, or the handle is not answering, the agent drops the handle, reconnects immediately, and replays settings (see #342). A handle whose requests time out repeatedly is dropped after a short bounded time (not 300 s) when enumeration shows a different/new path. Reconnect retry backoff caps at a few seconds while a Logitech device is enumerable.

**Key interfaces:**
- Agent HID worker: `on_device_arrival()` (called from the Win32 message window) that wakes the worker; the worker compares the enumerated HID path list to the active path.
- `connected_device` state and the agent->GUI pipe status message (e.g. `{"type":"device","connected":bool,...}`) must flip to disconnected promptly and to connected after recovery.
- Handle lifetime: closing the stale hidapi device must always happen (no handle leak per switch).

**Acceptance criteria:**
- [ ] Unit test (mock enumerator + mock device): enumeration returns a new path and the old handle returns nothing -> worker closes the old handle, opens the new, diverts, emits connected within one test tick (no 300 s wait).
- [ ] Unit test: 100 simulated switches leave 0 open handles besides the active one.
- [ ] Manual (BLE-capable Logitech mouse, ideally MX Master 3S; MX Master 2S over Unifying must not regress): Easy-Switch to another channel and back; mapped buttons (e.g. gesture, xbutton) work within 10 s with the agent running tray-only.
- [ ] While the mouse is absent the agent does not spin: enumeration at most once per backoff interval or per device-change event.

**Out of scope:**
- Linux/macOS.
- Pairing management.
- Multi-device (two Logitech mice at once) selection UI.
