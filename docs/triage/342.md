# #342 [Bug] DPI setting is lost/fails to apply after locking and unlocking Windows 11

> *This was generated by AI during triage.*

**State:** ready-for-agent (primary issue for the "device volatile settings lost after lock/sleep/wake" family; #278 is a duplicate, #298 is the Smart Shift / wheel-invert variant)

## Root cause (Mouser evidence)

Confidence: **likely** (mechanism confirmed in code; exact trigger on the reporter's PC not logged).

- The mouse keeps DPI (and Smart Shift, native wheel invert) in volatile memory; after a deep sleep it reverts to firmware defaults. Mouser only writes them at (re)connect time. The comment at `core/hid_gesture.py:897-909` shows Mouser knows only the button divert is persistent ("survives sleep/wake"); DPI is not.
- Replay of saved settings is triggered only from `Engine._on_connection_change` when `hid_features_ready` flips (`core/engine.py:1293-1338`; replay body `core/engine.py:1161-1257`).
- That flip only happens if the HID listener notices the device went away: after 3 consecutive request timeouts (`core/hid_gesture.py:3362`, asleep handling `core/hid_gesture.py:3374-3410`), a read/write exception (`core/hid_gesture.py:1451-1470`), or the 300 s asleep timeout (`core/hid_gesture.py:3363,3392`).
- Requests are only issued while idle polling is allowed, and that requires the UI to be visible: `core/engine.py:1340-1341` (`if not self._frontend_visible: return False`). With only the tray running there is no HID traffic, so the mouse can sleep, lose DPI and wake without Mouser noticing; no replay occurs. Opening the UI / touching DPI "fixes" it, matching the report.
- The Windows hook layer ignores lock/unlock and power events: `core/mouse_hook_windows.py:536-538` handles only `WM_DEVICECHANGE`/`DBT_DEVNODES_CHANGED`, and `_on_device_change` (`core/mouse_hook_windows.py:701-709`) only reinstalls the mouse hook, it never touches HID. A grep for `WM_POWERBROADCAST`/`WTS` in `core/` finds only macOS code (`core/mouse_hook_macos.py:465-518`, which calls `force_reconnect()` on wake; `core/hid_gesture.py:2093-2100` exists but Windows never calls it).

## Agent Brief

**Category:** bug
**Summary:** Re-apply all saved volatile device settings (DPI, Smart Shift, native wheel invert, haptic/force) whenever the mouse may have lost them: on Windows session unlock, system resume, or detected device wake, without any UI open.

**Current behavior:**
Saved DPI is written to the mouse only when the HID link is first established or re-established. After the PC locks/sleeps and the mouse firmware resets to default DPI, the resident process does not notice, so the mouse keeps the default DPI until the user opens the GUI and re-applies it.

**Desired behavior:**
The resident agent re-applies the saved device settings from `config.json` on each of these events, independent of whether the GUI is running:
1. `WTS_SESSION_UNLOCK` (and `WTS_CONSOLE_CONNECT`/`WTS_REMOTE_CONNECT`) session notifications for the agent's message window.
2. `WM_POWERBROADCAST` with `PBT_APMRESUMEAUTOMATIC` / `PBT_APMRESUMESUSPEND`.
3. Any HID++ traffic arriving after the link had been silent past a "device may have slept" threshold, or a hidapi reconnect.
4. HID link re-establishment (existing behavior).

Events are coalesced (debounce, single in-flight replay, one queued re-run). The device may not answer for a few seconds after wake: replay retries with bounded backoff (e.g. 3 attempts, total under 30 s) and then gives up quietly (no unbounded threads or buffers). Replay writes only settings that exist in config; absent keys are left alone. Idle with no event must produce no HID traffic (memory and wakeups stay minimal).

**Key interfaces:**
- Agent HID worker: a `replay_saved_settings(reason)` entry point callable from the Win32 message loop (session/power notifications) and from the HID reconnect path; must be idempotent.
- Win32 message window: register with `WTSRegisterSessionNotification` and handle `WM_WTSSESSION_CHANGE` and `WM_POWERBROADCAST`.
- Config: reuse `settings.dpi`, `settings.smart_shift_*`, `settings.invert_hscroll/invert_vscroll`, `settings.haptic_level`, `settings.force_sensitivity` from Mouser's `config.json` unchanged.
- Named-pipe status message to the GUI (if connected) after replay: success or "could not restore".

**Acceptance criteria:**
- [ ] Unit test (HID layer behind a trait with a mock device): firing `SessionUnlock` after a connected state causes exactly one `setSensorDpi` write with the saved DPI.
- [ ] Unit test: two events within the debounce window produce one replay; an event during an in-flight replay queues exactly one re-run.
- [ ] Unit test: a mock device that rejects the first 2 writes then accepts gets the DPI applied on the 3rd attempt; after max attempts the agent stops retrying and reports failure over the pipe.
- [ ] Manual (MX Master 2S over Unifying, GUI not running): set DPI 1600 in GUI, close GUI, confirm pointer speed; let the mouse sleep (or power-cycle its switch), `Win+L`, unlock; pointer speed is back at 1600 within 10 s without opening the GUI. Repeat with system sleep/resume.
- [ ] Agent idle HID traffic with no events stays at zero requests over 10 minutes (no polling added).
- [ ] No growth in thread count or private bytes after 100 lock/unlock cycles (scripted).

**Out of scope:**
- Periodic polling/verification of DPI while idle.
- macOS/Linux behavior.
- Bluetooth Easy-Switch re-detection (see #312).
- Changing the `config.json` schema.
